Tohfa — Unified Chatbot

PRODUCT RECOMMENDATIONS · FAQ ANSWERS · PROBLEM REPORTING — GEMINI-POWERED — ANTIGRAVITY IMPLEMENTATION PROMPT
What we're building: One chat endpoint in the existing Express/SQLite backend. A buyer types one message into one chat window. Gemini first classifies what they want, then the backend routes to one of three behaviors: recommend products from the catalog, answer a FAQ, or log a problem report and notify the seller/admin.
Why intent-routing instead of three separate bots: Running one cheap classification call before deciding what to do is far cheaper than calling Gemini three different ways every time, avoids nonsense like recommending products in response to "my order hasn't arrived," and is what makes this feel like one smart assistant to the buyer instead of three bolted-together features.

1. Architecture Overview

Step 1 — Buyer sends a message to POST /api/chatbot/message with their text and (if available) buyer/session id.
Step 2 — Classify intent. Backend sends the message to Gemini with a short classification prompt. Gemini returns one of: recommendation, faq, problem_report, or unclear.
Step 3 — Route and handle:
  • recommendation → pre-filter SQLite product list (basic keyword/category match) → send filtered list + buyer message to Gemini → Gemini returns structured JSON of recommended product IDs + reasons → backend maps IDs back to full product rows → return as cards.
  • faq → send buyer message + FAQ content (from a JSON/seed file, see Section 3) to Gemini → return its direct answer.
  • problem_report → Gemini extracts structured fields (category, description, related order/product if mentioned) → backend saves a ticket row in SQLite → sends email notification to admin/seller → confirms to buyer with a ticket reference.
  • unclear → ask a clarifying question instead of guessing.
Step 4 — Respond to the buyer in the same chat window regardless of which path was taken.
Cost/safety note: Classification + the actual task is two Gemini calls per message, not three. This is intentional — keep it that way rather than calling Gemini once per possible intent "just in case."

2. Database Changes (SQLite)

Two new tables are needed. Antigravity should check existing schema first and adapt naming/conventions to match what's already in the project (e.g. existing migration style, naming case).

-- chat_logs: every buyer message + classified intent + response (for debugging/improving prompts later)
CREATE TABLE IF NOT EXISTS chat_logs (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  buyer_id TEXT,                  -- nullable if buyer isn't logged in
  session_id TEXT NOT NULL,
  message TEXT NOT NULL,
  intent TEXT NOT NULL,           -- recommendation | faq | problem_report | unclear
  response TEXT NOT NULL,
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);

-- problem_reports: tickets raised through the chatbot
CREATE TABLE IF NOT EXISTS problem_reports (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  buyer_id TEXT,
  session_id TEXT NOT NULL,
  category TEXT,                  -- e.g. delivery, payment, product_quality, account, other
  description TEXT NOT NULL,
  related_order_id TEXT,
  related_product_id TEXT,
  status TEXT DEFAULT 'open',     -- open | in_progress | resolved
  created_at DATETIME DEFAULT CURRENT_TIMESTAMP
);

4. Gemini Prompts

4a. Intent classification prompt

You are an intent classifier for an e-commerce chatbot for "Tohfa", an Indian
handmade artisan marketplace. Classify the buyer's message into exactly ONE
of these categories:

- "recommendation": buyer wants product suggestions, gift ideas, or is
  describing what they're looking for.
- "faq": buyer is asking about policies, shipping, returns, payments,
  how the platform works, etc.
- "problem_report": buyer is reporting an issue — damaged item, wrong item,
  late delivery, payment problem, account issue, complaint.
- "unclear": message doesn't clearly fit any category above, or is just
  small talk / greeting.

Respond with ONLY valid JSON, no markdown, no preamble:
{"intent": "recommendation" | "faq" | "problem_report" | "unclear"}

Buyer message: "{{message}}"

4b. Recommendation prompt

You are a helpful shopping assistant for Tohfa, an Indian handmade artisan
marketplace. Recommend ONLY from the product list provided below — never
invent products that aren't in the list. If nothing in the list is a good
fit, say so honestly instead of forcing a match.

Buyer request: "{{message}}"

Available products (JSON):
{{filtered_product_list}}

Respond with ONLY valid JSON, no markdown, no preamble:
{
  "recommendations": [
    { "product_id": "...", "reason": "short reason this fits, 1 sentence" }
  ],
  "note": "optional 1-sentence note if no great match exists"
}

Return at most 5 recommendations, ranked best first.

4c. FAQ prompt

You are a support assistant for Tohfa, an Indian handmade artisan marketplace.
Answer the buyer's question using ONLY the FAQ content below. If the question
isn't covered, say you don't have that information and suggest they report
it as a problem instead so the team can help directly. Keep the tone warm
and concise — 2-4 sentences.

FAQ content (JSON):
{{faqs}}

Buyer question: "{{message}}"

Respond with plain text only (no JSON, no markdown).

4d. Problem report extraction prompt

You are extracting structured details from a buyer's problem report for
Tohfa, an Indian handmade artisan marketplace. Read their message and
extract what you can. Do not invent details that aren't present.

Buyer message: "{{message}}"

Respond with ONLY valid JSON, no markdown, no preamble:
{
  "category": "delivery" | "payment" | "product_quality" | "account" | "other",
  "description": "clean 1-2 sentence summary of the issue in buyer's intent",
  "related_order_id": "string or null if not mentioned",
  "related_product_id": "string or null if not mentioned"
}

7. Replacing the Existing Report-a-Problem Page

Important — do this deliberately, not as an afterthought. Tohfa already has a separate report-a-problem page/form. Leaving both live at once means buyers will use whichever they stumble on first, your team gets tickets from two different places with two different shapes, and you end up maintaining two systems that drift apart. The goal is one path only.

8. Frontend — Floating Mascot & Chat Panel

What this is: A small floating mascot icon, fixed to the bottom-right corner of the screen on every page, on both web and mobile. Tapping/clicking it opens the chat panel — the single entry point for product recommendations, FAQ answers, and problem reporting. Closing it shrinks back to just the mascot.

8a. Visual direction

Stays inside the existing Botanical Artisanship system rather than introducing new colors. Mascot bubble uses Forest (#3D6B4F) as its base with a Gold (#C8973A) ring/accent on hover or when there's an unread response — small enough to feel like a companion, not an ad. Chat panel itself uses Parchment (#F7F3EC) background, Forest for headers/sent messages, Sage (#8FAF82) for bot message bubbles, Playfair Display for the panel title, DM Sans for body text. This is a placeholder icon (simple leaf or speech-bubble glyph) — swap in a real mascot illustration later without changing layout/behavior.

8c. Chat panel internal structure

Header: mascot icon (small) + "Tohfa Assistant" title + close button
Message list: scrollable, buyer messages right-aligned (Forest background, white text), bot messages left-aligned (Sage background, dark text)
Recommendation responses render as small product cards inline in the message list (image, title, price, 1-line reason) rather than plain text — each card links to the product page
Problem-report confirmation renders as a distinct "ticket" style message (bordered, gold accent) showing the ticket reference so it doesn't look like a normal chat bubble and gets noticed
Input bar: text input + send button, fixed at bottom of panel
Optional (nice-to-have, not blocking): 2-3 quick-reply chips above the input on first open — e.g. "Find a gift", "Track my order", "Report a problem" — to nudge buyers who don't know what to type

9. What's Deliberately Out of Scope (for now)

No embeddings/pgvector — catalog is small enough to pre-filter + pass directly to Gemini. No multi-turn conversation memory beyond what's needed per message — each message is classified and handled independently for now; conversational follow-up ("show me cheaper options") can be added once the basic flow is working. No admin dashboard for problem reports yet — tickets land in SQLite and trigger an email; a dashboard view can be a later addition to the existing Admin Panel. No real mascot illustration yet — placeholder icon ships first, design swap is a drop-in replacement later since layout/behavior don't depend on the visual.
