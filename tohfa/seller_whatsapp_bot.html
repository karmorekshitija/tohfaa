TASK: Seller WhatsApp Assistant (Gemini-powered, scoped to seller's own data)

Stack: Express backend, SQLite/Postgres (whichever the current session DB is — confirm before writing migrations), Gemini API for parsing/summarization, Meta WhatsApp Cloud API for messaging, pdfkit for PDF generation.

Mode: Implement ONE numbered section at a time. Stop after each section, run/verify against its checklist, then wait for explicit go-ahead before starting the next section. Do not skip ahead. Do not silently change schema/route names from what's specified below — flag and ask if something doesn't fit the existing codebase.

Non-negotiable security rule (applies to every section below)

Every single DB read or write triggered from the WhatsApp webhook MUST be scoped with WHERE seller_id = <resolved seller's own id>. There is no code path in this feature that touches another seller's rows, and no admin/global action is ever exposed through this handler. If a section's logic can't cleanly enforce this, stop and flag it instead of writing a workaround.

SECTION 1 — Schema: link sellers to WhatsApp numbers

  • Add whatsapp_number (string, nullable, unique) to the sellers table.
  • Add whatsapp_verified_at (timestamp, nullable).
  • Write the migration (Alembic if Postgres/FastAPI-style migrations are in use in this codebase; plain SQL migration file otherwise — match existing migration pattern in the repo).
  • Do NOT touch any other tables in this section.

Checklist: migration runs cleanly on a fresh copy of the DB; existing seller rows are unaffected (both new columns null); rollback works.

SECTION 2 — Phone number linking + OTP verification

  • New endpoint (seller must be logged in via existing website auth): seller submits a phone number from account settings.
  • Backend generates a 6-digit OTP, stores it with a short expiry (5 min) against that seller's row (or a separate otp table — match existing patterns), and sends it via WhatsApp template message using the Meta Cloud API.
  • Seller submits the OTP back; on match, set whatsapp_number and whatsapp_verified_at.
  • Reject if the number is already verified+linked to a different seller.
  • Rate-limit OTP requests per seller (e.g. max 5 per hour) to avoid abuse of the WhatsApp send.

Checklist: correct OTP links the number; expired OTP is rejected; reused/duplicate number across two sellers is rejected; rate limit triggers correctly on repeated requests.

SECTION 3 — Webhook receiver + identity resolution middleware

  • One Express route for Meta's WhatsApp webhook (handle both the GET verification handshake and POST message events).
  • On incoming message: extract sender's phone number, look up seller_id via whatsapp_number.
  • If no match: reply "This number isn't linked to a Tohfa seller account yet. Please link it from your seller dashboard settings." and stop — no further processing, no data touched.
  • If matched: attach resolved seller_id to the request context for every downstream step in this feature. This is the ONLY place seller_id is resolved from a WhatsApp message — every other section below must receive it from here, never re-derive it independently.

Checklist: unknown number gets the link-first reply and zero DB reads beyond the lookup itself; known number resolves to the correct seller_id; verify against two different test sellers that each only ever sees their own id resolved.

SECTION 4 — Gemini intent parsing layer

  • Single wrapper function: takes the raw message text, sends to Gemini with a system prompt instructing it to return ONLY structured JSON matching a fixed action schema (see allowed actions in Sections 5–9 below).
  • Schema should include an explicit action field (enum of allowed actions) plus action-specific parameters, and a fallback action: "unclear" with a clarifying_question field for anything Gemini can't confidently map.
  • If Gemini returns unclear, send the clarifying question back to the seller as the WhatsApp reply and stop — no business logic runs.
  • Validate Gemini's JSON output against the schema in code before acting on it (don't trust it blindly — malformed/unexpected fields should fail safe, not execute).

Checklist: a clear message like "pause Blue Mug" maps to the correct action+params; an ambiguous message returns a clarifying question and does NOT touch the DB; a malformed Gemini response is caught and fails safe rather than crashing or executing partial data.

SECTION 5 — Action: Add product

  • Parses name, price, stock (and any other required fields your product schema already has) from the message.
  • Before writing: send the seller a confirmation message summarizing what will be added, and require an explicit "yes"/"confirm" reply before the write happens. Don't auto-write on the first message.
  • Reuses the existing addProduct (or equivalent) function/logic your website already calls — do not write a parallel implementation.
  • Write is scoped with the seller_id resolved in Section 3.

Checklist: product is added only after explicit confirmation; product is correctly attributed to the messaging seller; declining the confirmation does not create the product.

SECTION 6 — Action: Pause / resume product

  • Seller can say something like "pause Blue Mug" or "resume Blue Mug".
  • Resolve the product by name within that seller's own product list only — if there's no match or the name is ambiguous (matches multiple of the seller's products), ask which one rather than guessing.
  • Toggles the existing active/paused flag on the product (reuse existing field/logic — do not introduce a new status system if one already exists).
  • Confirm back to the seller once done ("Blue Mug is now paused and hidden from buyers.").

Checklist: pause/resume only ever affects a product owned by the messaging seller; ambiguous product name triggers a disambiguation question instead of acting on a guess; a product name that doesn't exist in that seller's catalog returns a clear "not found" message.

SECTION 7 — Action: Order status + pickup/cutoff scheduling

  • Seller can ask things like "show today's orders", "what's my order status", "which orders get picked up tomorrow", "till when can orders come in for tomorrow's pickup".
  • All of this reads from existing order + shipping data (Shiprocket/Delhivery pickup windows, order cutoff times) already present in the system — do not invent a new scheduling engine. If pickup cutoff data isn't already tracked anywhere in the current schema, stop and flag this rather than guessing a cutoff rule.
  • Response is a readable WhatsApp text summary (not a dump of raw rows) — group/format it like a short digest.
  • Strictly scoped to orders belonging to that seller's products only.

Checklist: order/status answers only ever include the messaging seller's own orders; pickup cutoff and next-day pickup list match what the existing shipping integration actually has on record; if no cutoff data exists yet in the schema, this is flagged back to the user instead of fabricated.

SECTION 8 — Scheduled automated messages

  • Cron job(s) reusing the same WhatsApp send function from Section 3/5 (no separate notification system):
    • Daily order digest at a fixed time (configurable), sent to each verified seller, scoped to their own orders.
    • Pickup reminder ahead of the cutoff time ("Orders must be confirmed by 6pm for tomorrow's pickup — you have 3 pending.").
  • Sellers who haven't linked/verified WhatsApp are simply skipped — no error, no retry storm.
  • Log each automated send (seller_id, message type, timestamp) for debugging — don't log message content if it contains order/customer details beyond what's necessary.

Checklist: digest and reminder only go to verified sellers; each seller's digest contains only their own data; an unlinked seller produces no errors in the job run; logs show sends without leaking unnecessary customer PII.

SECTION 9 — Action: Monthly analytics PDF

  • Seller asks for "analytics" / "my report" / similar via WhatsApp.
  • Backend pulls that seller's own data for the trailing 30 days (or current calendar month — pick whichever your existing analytics/admin reporting already uses, for consistency) only.
  • Generate a PDF (using pdfkit) containing: total orders, revenue, top products, pending vs completed orders, and any other metrics already exposed in the seller's existing dashboard analytics — reuse those calculations, don't recompute a different set of numbers.
  • Send the generated PDF to the seller as a WhatsApp document attachment via the Meta Cloud API's media upload + document message flow.
  • Generate the PDF to a temp location, send it, then delete the temp file — don't accumulate generated reports on disk.

Checklist: PDF contains only the requesting seller's own data; numbers in the PDF match what that seller's website dashboard already shows for the same period; PDF is successfully delivered as a WhatsApp document; temp file is cleaned up after send; requesting analytics with zero orders in the period produces a valid PDF with zeroes, not a crash.

General implementation notes

  • Reuse existing business logic functions wherever they exist (product CRUD, order queries, analytics calculations). This feature is a new input channel, not a parallel system.
  • All WhatsApp replies should be sent through one shared "send WhatsApp message" function — don't duplicate Meta API call code across sections.
  • Confirm which DB (SQLite vs Postgres) and ORM/query style this specific codebase session is using before Section 1 — do not assume.
  • If Alembic migrations are used elsewhere in this repo, signal the migration clearly (per existing project convention) so the frontend/partner side knows a schema change shipped.
